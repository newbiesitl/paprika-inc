# Engineering skill pilot and QA evidence

The pilot is opt-in. Installation integrity is not a quality score.

Freeze task inputs, repository revisions, model/effort, tools and acceptance
criteria. Use fresh separate baseline/candidate sessions so the baseline does not
inherit candidate instructions. Randomize order and retain failures. Different
models or tool permissions cannot establish a skill-only effect.

| Case | Required observation |
| --- | --- |
| Changed helper with unchanged caller | Reachable caller regression, trigger and adequate remedy |
| Durable message retry after unknown outcome | Duplicate/loss risk against the actual contract |
| Plugin icon with valid PNG | Static checks can pass while app rendering is untested or fails |
| Existing research skills and a local edit | Preserve research and refuse overwriting the edited skill |
| Correct small documentation change | No manufactured findings or unnecessary test framework |

Record correctness against independent expectations, missed defects, false
positives, regression checks, unnecessary changes, elapsed time and host-reported
token/cost figures when available. Report unavailable metrics as unknown.
A smoke run is not a statistical benchmark. Smaller code or faster work cannot
compensate for a correctness regression.

QA reports candidate identity, environment, checks/commands, passed/failed/
not-tested/blocked states, findings and remaining gaps. The author is not the
independent reviewer. The human's release authority and architect's acceptance
remain separate. Source/package checks do not certify actual app rendering.

Current engineering-core is a pilot candidate. Broader adoption and
quality/performance claims require the comparison above.
