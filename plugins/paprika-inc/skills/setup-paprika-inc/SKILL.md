Use `$setup-paprika-inc` for onboarding and the user's chosen existing chat for first-staff discussion. Reuse established inputs. A generic setup invocation begins discussion/planning; installation, file writing, Git publication, bootstrap and service connection need their applicable human request. Continue unchanged authorized work without redundant confirmation. File generation alone creates no chats or powers.

Follow [the concrete MVP workflow](references/mvp-workflow.md), including its blueprint, commands, native host loop and explicit resume. For requested installation, inspect the host's supported local plugin/Plugin Creator installation tools and select the prepared Inc directory, never the repository/vendor tree as a marketplace. Do not claim installation from ZIP validation or automatically upload/deploy an account plugin. Build commands install nothing.

For optional scientific roles, follow [research-core setup](references/research-core.md): select the reviewed set in the role manifest, explicitly plan/install into the chosen project's .agents/skills/, and report each skill's integrity and capabilities separately. Do not install the upstream Scientific Agent Skills plugin or its full catalog. Selected project skills may appear in that project's selector; role references do not restrict discovery. Missing optional tools/services must not block basic Markdown synthesis or critical appraisal.

For requested work tracking and resumable handoffs, follow
[flexible work checkpoints](references/work-checkpoints.md). Reuse the company's
work/knowledge index, configured paths and role contracts; create records only
within the requested scope. During read/report onboarding, read existing adopted
work records when relevant without creating tasks or treating proposed workflow
text as adopted. Later versioned notices need the actual communication grant;
record read/adoption receipts separately from initial onboarding.

The local native on-demand workflow needs no separate Messenger product/service. When service connection is requested or Messenger already exists, discover the exact selected existing owner-private Paprika Service/App through supported authenticated native metadata and configuration/board reads. Preserve App/OAuth identity, database/history, service type/configuration, authoritative delivery/receiver state and paused/off preferences. Missing discovery/authentication is not proof a new service is needed. Never invent App IDs/endpoints, create a replacement service, install a second Messenger product or copy another owner's binding.

For an explicitly requested live company initialization/creation, establish its dedicated Messenger board using [company board setup](references/mvp-workflow.md#dedicated-company-board). Reuse the verified board or create it if absent; never use `main` without an explicit human instruction. This Inc company rule takes precedence over Messenger's generic default. Keep the binding private and pass it explicitly to each board operation. A planning/file-authoring request alone has no remote effects.

An optional private bound export uses `python3 scripts/prepare-plugin.py --service-binding <private-native-report.json> --output <private-output-directory>` from the owning source checkout, with the exact report format in [the workflow](references/mvp-workflow.md#installation-and-existing-service-binding). It references one existing App in both manifests; the builder cannot authenticate the report, create an App/service or prove installation. Save/install/connect only when requested through supported host tooling, then verify authenticated access separately. Inc release, exact bundled Messenger source and running API are distinct records. A newer deployment requires capability review, never automatic downgrade.

Use actual saved local project metadata and native `create_thread` with a local project target, then independently verify catalog membership/cwd and read/report results. Missing project registration gets the one-time app handoff. A ChatGPT caller without a supported local route hands off to local Codex. Do not substitute ephemeral/backend sessions or edit Codex private databases.

Preserve [coexistence](references/coexistence.md): only Inc's navy product and two Inc skills are added; no duplicate Messenger product/icon/command. A required Paprika Service backend App may appear separately; do not hide it using unsupported visibility flags. Source inclusion does not start/deploy services. No automatic receiving, singleton/race enforcement, failover, transfer or self-adoption is part of this MVP. Keep outstanding installation/native/UI evidence distinct from fixtures.

For an agreed engineering/QA role, follow the optional [engineering-core workflow](references/engineering-core.md). It selects one Paprika review skill with pinned provenance and adapted operating guidance, without upstream plugins or session hooks. Installation is project-local and explicit; onboarding is read/report only, not review-quality certification.

During company discussion and role creation, use [role recommendations](references/role-recommendations.md). Recommend a Coordinator and a separate Release Engineer for IT and research companies when workflow volume warrants them; keep technical/scientific review with other roles. Discuss model/effort preferences and use exact human-approved native parameters. Templates neither create chats nor authorize publication.

For an owner-authorized release workflow, follow [delegated reviewed merges](references/role-recommendations.md#delegate-reviewed-merges).
Use [proportionate company QA](references/role-recommendations.md#proportionate-company-qa)
for meaningful validation checkpoints; do not dispatch QA for every task or PR.
Release Engineer may execute merges after independent related-role review and QA
where the selected company policy or assigned acceptance gates require it,
within the selected owner's actual scoped grant. Reuse unchanged authorization;
verify current-head reviews, CI and protections. An existing PR-only maintainer
exception requires explicit coverage in that grant. Never self-approve, change
protections or evade a host denial. Publication and installation remain separately
authorized. These instructions do not create a grant for another company.
