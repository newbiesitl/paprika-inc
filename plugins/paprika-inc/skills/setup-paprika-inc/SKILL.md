Use this skill for `$setup-paprika-inc`, “set up Paprika Inc”, “initialize this company”, or first onboarding. In this skeleton, setup/init means prepare a plan, not execute initialization. Honor current human assignments and host permissions; do not create/recreate role chats, enroll/adopt a company, install/publish a plugin, provision a service, connect receivers, or enable background work.

Follow [Inc-only and Messenger-already-installed onboarding](references/coexistence.md). Inc exports only its own navy product identity and `paprika-inc` / `setup-paprika-inc` skills; never install/register a bundled Messenger product or duplicate its commands/icon. A required **Paprika Service** App may appear separately; do not invent visibility flags to hide it. Future binding must reuse the same verified compatible App/OAuth identity, database/history and authoritative delivery/receiver state. Keep Inc release, exact bundled Messenger source and running service evidence distinct.

1. Resolve the user's selected repository. Reuse the established choice; ask only if it is absent or ambiguous. The package location, company name, matching directory, role label or manifest alone does not establish repository or project identity.
2. Run the contained helper: `node <this-skill-directory>/../paprika-inc/scripts/inc.mjs plan --repo <selected-repository>`. Follow [Paprika Inc](../paprika-inc/SKILL.md) for runtime/input errors. Preserve and report completed local checks even when other prerequisites remain pending.
3. Before any future provisioning decision, identify the selected existing owner-private Messenger service. Discover available read-only service/Sites metadata tools in this host. If available, inspect the exact selected service's authenticated configuration, runtime version/capabilities and owner/private binding. Preserve service type, database, history, existing addresses and paused/off receiving. Multiple plausible services require a choice; an authentication/discovery failure is not evidence that no service exists. Never downgrade a newer service or create a replacement to repair uncertainty. Service discovery and binding are not implemented by the local helper; tool observations are a separate read-only checkpoint, never a claim that Inc initialization succeeded.
4. If useful, pass only the minimal non-secret fields in [boundaries](references/boundaries.md) to `--service-report` in private scratch storage. The helper deliberately treats reports as unverified. Do not persist real IDs, machine paths, grants, credentials or conversation content into public source.
5. Report definition validity, pending host/project identity evidence, private enrollment/registry, adoption, service discovery/App binding, lifecycle operations and receiving separately. Explain the next prerequisite and retain unknown states. The package is an owner-neutral local skill kit; a later service-bound account package requires a verified existing App binding and supported installation flow. This package contains no App ID, endpoint or OAuth registration.

The first slice implements no apply path. Continue only with read-only work already authorized; return an explicit pending capability for requested mutations. On-demand is the desired default, but this plan creates no receiving route. Only future separately authorized and verified setup may report initialization, created roles, adoption or automatic receiving. A briefing or role response is not managed lifecycle adoption.
